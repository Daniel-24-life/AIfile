# Application Record

I used the handbook rules during one repository maintenance cycle and recorded the changes below.

## Task

Review a public AI portfolio for reproducibility, learning value, clarity, and disclosure risk.

## Handbook Rules Applied

| Rule | Application |
| --- | --- |
| Map the repository before editing | Compared the remote tree, local changes, project indexes, code packages, and public status labels. |
| Keep state outside chat | Used a staged task plan and preserved unrelated Daily Brief work. |
| Separate creation from review | Completed the outsider review before changing code or public wording. |
| Treat tests as evidence | Ran each public skeleton independently and added counterexample tests. |
| Fail closed on unknown input | Changed unknown planes, evidence classes, creator fields, and missing identifiers from pass-through behavior to blocked decisions. |
| Require a publishing checkpoint | Prepared local changes for review without pushing them to GitHub. |

## Before And After

| Area | Before | After |
| --- | --- | --- |
| Quant routing | Unknown plane could pass policy review. | Unknown plane, priority, and action type are refused. |
| Evidence classification | Unknown evidence class could accept a real-execution claim. | Unknown evidence classes block all claims. |
| Creator review | Unknown field values could reach `approved`. | Unknown fields and missing IDs are blocked. |
| Mailbox duplicate check | Duplicate status arrived as a caller-supplied boolean. | The gate checks the action ID against recorded IDs. |
| Public status | Two published packages still carried a local-review label. | Published packages use the public status label. |

## Verification

The repository-level verification entry runs each package in isolation so their local import paths do not collide. Public evidence samples use synthetic identifiers and contain no account, contact, strategy, source-list, or operating data.
